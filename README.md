# Weft — private event planning pilot

Event planning with Google sign-in, a server-backed project workspace, and encrypted organizer-only booking details. This branch adapts the app to Next.js on Vercel, Turso/libSQL and private Vercel Blob storage. New real workspaces start empty; the Field Day sample remains in the separate demo.

The Vercel migration is not a completed hosted rollout: credentials, isolated storage, Google callbacks and live end-to-end checks still need configuration and verification. The existing private Sites app and its data remain untouched; nothing is copied or linked automatically. Follow the [Vercel deployment runbook](docs/vercel-deployment.md). Pushing and publishing require owner approval of the reviewed revision under [the engineering loop](docs/engineering-loop.md).

## Implemented behavior

- Tasks, owner acceptance, completion reports, organizer verification, comments, follow-up drafts, event context, and contextual feedback rules use durable Turso/libSQL storage through the existing SQL interface.
- Project APIs check authenticated membership server-side. Google sign-in requires a verified email and establishes a stable `google:<sub>` identity; incoming Sites identity headers are never trusted. The initial owner is bootstrapped from the configured allowlisted email. Teammates join individual projects using email-specific, expiring invitation links. Browser actor selection cannot grant permissions.
- Workspace writes use a compare-and-swap revision. Other-tab conflicts require an explicit page reload; drafts are never silently rebased onto newer data.
- Flight/hotel/transport/venue references are encrypted using AES-256-GCM with a separate secret server key. Gmail credentials and text previews use distinct authenticated encryption contexts. Private data never goes into shared exports, browser localStorage, or task notes automatically.
- Gmail imports use read-only Web OAuth, PKCE, expiring single-use state bound to the signed-in owner, server-side refresh tokens, and revocation. After authorizing Gmail, select projects and separately approve automatic AI checks. A separate dedicated Gmail connection sends project invitations with `gmail.send`, `openid` and `email` permissions; it does not read that mailbox.
- Automatic detection drafts private summaries of matching or possibly related incoming emails. The organizer can edit the summary, correct its project, and explicitly approve sharing; tasks still require a separate approval. Manual label import remains available under advanced settings. Private views show the 100 most recent matching imports, with originals collapsed and encrypted separately.

## Projects and setup

`/` is the Projects homepage. `/setup` creates a separate, empty project and then opens the optional `/plan?project=<id>` review step; `/setup?project=<id>` edits only that project's settings. `/project?project=<id>` opens its workspace. Creation is authenticated, server-persisted and retry-safe, independent of AI availability. Existing data stays under `main`; no tasks, guests, files or bookings are moved or cleared. New projects use an owner-authorized registry and explicit URL IDs so two tabs cannot switch each other's active project. Migration `0004` adds the registry and a booking scope defaulting to `main` for old records.

The hosted workspace shows a neutral loading screen until its authenticated project has rendered. It does not briefly show the sample event or inactive task controls. Failed data or app loading provides retry and navigation without exposing an uninitialized workspace.

An unfinished **Getting started** guide shows its next saved step on Projects. Resume uses the original guide project; ordinary project cards still open without the guide. The resume card is private to the signed-in account and reading it does not record a click, view or completion.

Gmail and guest-list imports are optional. The Gmail connection and optional manual label remain account-wide. Automatic matches are privately associated with one selected project; legacy manual imports remain available across the owner's projects. Reviewed summaries explicitly target a project. Tasks, guests, files, private bookings, suggestions and resource caches are project-scoped. Setup uses organizer authorization, origin verification, field validation and revision-checked edits. Failed saves preserve form values. Event date and location are optional. There is a 100-new-project organizer limit.

## Accounts and invitations

`/account` shows the current Google identity and sign-out. Organizers open **People → Team access** (or Invite), connect the dedicated Weft Gmail account, enter a teammate's Google sign-in email, and choose **Send invitation**. `/join?invite=…` checks the email before displaying project details; accepting atomically creates or reuses the account and grants access to that project. Links are single-use, expire in 7 days, and can be revoked. Creation and acceptance retries do not duplicate members. Tokens are stored as hashes plus an organizer-readable encrypted copy, never in shared task state.

Invitation setup uses the owner-configured Google Web client and `/api/gmail/callback` URI, distinct from sign-in's `/api/auth/callback/google`. Enable Gmail API, add the dedicated account as a testing user when applicable, and configure `gmail.send`, `openid` and `email` scopes. The owner configures the client and connects the dedicated account once; invitees need no Google API setup. Google UserInfo verifies the sender address. Import and sender connections must use different accounts; separate encrypted tokens, state tables and commit guards prevent one connection from replacing the other. Migration `0006` adds sender authorization, delivery state and send-attempt records without modifying existing invitations.

Only an explicit organizer action sends an invitation. Its recipient, project name and acceptance URL are server-owned. Durable send claims prevent double-click/network retries from dispatching twice. Status is **sent** only after Gmail returns a message ID; this means Gmail accepted the request, not guaranteed inbox delivery. Definitive rejection permits a manual retry after a minute; timeout, ambiguous errors, or an unrecorded receipt become **sending not confirmed**, never automatically retried. Check Gmail's Sent folder before revoking/replacing an uncertain invitation. Limits: 3 attempts per invitation and 50 attempts per rolling 24 hours across the organizer's projects. No guest-list mail or automatic task reminders are sent.

Google sign-in is authentication, not project access. Invited teammates see only their joined projects, can claim unassigned tasks, report their own progress/completion, comment, and contribute guest records/files. They cannot edit task metadata, manage access, connect Gmail, read private bookings/original emails, or use the owner's demo. There is no password database or separate password-reset flow. Sign-out requires confirmation and a CSRF-protected POST. If a Vercel deployment also has Deployment Protection enabled, a tester needs that separate platform admission; app invitations do not change it. The old private Site retains its existing access policy.

After accepting an invitation, teammates get their own welcome in the joined project, separate from the organizer’s setup guide. It points to their assignments, unassigned work when available, and Event info, Timeline and People. Pending assignments also show on a returning teammate’s Overview. Before accepting, they can see the expected **Done when** outcome, required work still outstanding, and whether a task is blocked or waiting for organizer help. **Back to assignment review** restores only selections that are still eligible and match the reviewed task revisions. Accepting records who’s responsible; it doesn’t resolve blockers or mark work complete. Joining and opening the review don’t change tasks.

After confirming a single new acceptance from **My tasks**, the teammate can open that exact assignment from a confirmation at the top of the page. If the task is ready to work on, the confirmation also links to its **Next up** controls or the existing swap picker when all three slots are full. Opening the controls never adds or replaces a commitment. The assignment review distinguishes unavailable prerequisites from work still in progress.

The organizer’s first-project guide previews optional AI planning, then offers **Try drafting a plan with AI** beside the first task they just saved in Shared tasks. The same entry stays available in the active project guide when they move to another page or resume later, and in Getting started. It’s not part of the separate teammate welcome. The planner shows a sample brief and three visible steps: describe the event, generate a private draft, and review what to add. Its shortcut follows the real brief, draft controls, review, and receipt; it points to the no-AI starter checklist if AI is unavailable. Nothing is sent to the provider until the organizer explicitly generates a draft, and nothing is shared until they add selected items. **Save and return to guide** keeps the private brief, edits and item selections for later, returning to the current guide step only after the save is confirmed. Import or clear any pasted checklist text first. The planner is also available from **Overview → Build a plan**.

Removing access preserves task/comment history and marks the teammate inactive for new assignments. Server writes recheck active membership and its generation at commit, so remove/reinvite cannot revive stale task, file or helpful-link requests. Workspace revisions advance on team changes; open clients refresh every 20 seconds or on focus, and stop displaying a project when access is denied. Previously downloaded information cannot be recalled. Limits per project: 50 active teammates, 500 historical memberships and 500 invitations total. Migration `0005` adds project memberships and invitations without changing existing projects or ciphertext.

The homepage adapts `ProjectsHome.tsx` and `projects-home.css` from the existing Gather Lovable design workspace, commit `f7669b53ebacbefa76e8bf8f85e8cd28dae997d4`. It uses Gather's existing theme and validated setup form. Lovable preview data and storage are not part of the production app.

## Pilot boundaries

- Project data remains restricted by server-side membership. The Vercel sign-in page may be publicly reachable; it is not a replacement for Deployment Protection when an entire preview must be private. No access settings on the existing private Site are changed. Account-free attendee links are not enabled. Teammates retained in older sample workspaces are examples, not real accounts.
- Continuous planning checks and shared task-change suggestions use conservative local rules and event feedback. Organizer-requested starting plans and private Gmail relevance checks use Groq Responses structured output and the server-only `GROQ_API_KEY`. There is no OpenAI or paid-provider fallback. No autonomous email sending, live RSVP integration, or Gmail push notifications. Closed-app email checks require the verified cloud schedule below.

Planning suggestions recalculate on workspace reads and edits. Visible workspaces check for changes every 20 seconds (4 seconds in the demo), when Suggestions opens, and when returning to the page, including browser Back. Clock-driven checks can update without a saved project edit. The open Suggestions panel refreshes in place; task, guest and email drafts defer shared-state updates until safe. Covered and dismissed checks stay suppressed. Nothing runs while the app is closed; reopening checks the current state and time. Suggestions do not automatically create tasks.
- Google OAuth needs an actual Google Cloud Web client: enable Gmail API, configure consent/testing users and the relevant import/sending scopes, and add the exact redirect URI displayed in settings. Google may require verification for wider deployment; testing grants may need reconnecting after seven days.
- Gmail ingestion tests use mocked provider responses; they do not prove live mailbox ingestion. Do not enter passport or payment-card data. This pilot has not had an independent security assessment.
- Import disconnect revokes Google's import-account grant but retains imported previews and shared summaries. Sender disconnect removes its tokens and pending authorizations from Weft; Google grant revocation is available in the dedicated account's Google settings. Already-dispatched email cannot be recalled. Changing the Google client while either connection is active is denied. Original retention controls and account deletion UI are future work.
- Editing `GATHER_OWNER_EMAIL` does not revoke an already-bound owner: ownership changes need deliberate membership migration. Do not rotate the encryption key without migrating existing ciphertext.
- Private view hiding clears visible records but is not sign-out. Use Sign out to terminate account access.

## Automatic Gmail checks

Publication, a Groq free account/key, fresh mailbox consent and an authenticated cloud schedule must all be verified before calling detection live. Tests use mocked responses, not live email. Stay on Groq’s Free plan without enabling billing: free access is an account setting, not an API flag. Enable Zero Data Retention in Groq Data Controls before processing private emails. Ordinary users need no Groq account or key.

The owner selects up to ten owned projects and explicitly consents to sending email text plus project names/date/location and up to 60 active task titles per project to Groq. No guests, uploaded files, booking records, task comments or attachments are included. Text previews are limited to 24,000 characters, with the first 12,000 eligible for classification. Requests use no tools, strict structured output and server validation. Groq does not support the OpenAI `store` request option; retention is controlled by the Groq account. Clearly unrelated content is discarded; only opaque, expiring deduplication receipts remain. Matching/uncertain originals and drafts are encrypted; nothing is automatically shared. AI relevance and summaries can be wrong. Old provider consent never authorizes Groq: jobs pause before network access until fresh versioned consent. Re-consent preserves checkpoints, pending IDs, receipts and private summaries.

Initial enrollment scans the last seven days. Gmail history then catches incoming messages without labels, including archived mail and self-addressed mail. The initial history anchor is saved before backfill; page queues are checkpointed before processing and the final history ID advances only after processing every candidate. A 404-expired history cursor starts a disclosed seven-day recovery; earlier gaps can require manual import. Reconnecting or changing the Gmail label invalidates enrollment, requiring re-enabling detection. Pause keeps existing imports; re-enabling the same connection and project set resumes saved progress.

Each bounded run handles at most one queued message, one Gmail page and one AI request to reduce free-tier token bursts. Catch-up is gradual, not instant. Database leases prevent overlapping workers and stale writes; the pinned Gmail token cannot switch mailboxes mid-run. Attempts are capped at 250 candidate emails per account/day, including provider failures. A full-payload size guard rejects oversized context before consuming this allowance; it pauses checks with guidance instead of repeatedly retrying an oversized request. Queued emails remain intact. This guard is not an exact tokenizer or a guarantee of remaining provider quota. Groq 429 responses retain the cursor and respect bounded Retry-After backoff (one hour when absent); credential failures are paced hourly. Existing imports are not duplicated. Migration `0008` remains unchanged.

### Cloud runner setup and operation

Background checks are **off by default** and no cron schedule is included in `vercel.json`. After Groq setup, mailbox authorization, fresh AI consent and an explicitly approved schedule, the operator may enable `GMAIL_BACKGROUND_MODE=vercel-cron` with a random server-only `CRON_SECRET` of at least 32 characters. Vercel Cron then makes an authenticated `GET /api/gmail/automatic-run`, passing the secret as a bearer token. The endpoint rejects unauthenticated calls, caller identity headers, Origin headers and query overrides. It only processes already-enrolled, still-authorized mailboxes; it cannot create consent or impersonate a user.

Do not reuse the old Sites dispatch credential or `owner-private` mode on Vercel. Follow the [runner activation and verification steps](docs/vercel-deployment.md#optional-background-gmail-checks). A successful HTTP response or `not_due` result alone is not proof that an email was ingested. Groq credentials, live mailbox ingestion and unattended scheduling remain unverified until that full flow is exercised.

The settings page distinguishes configured background scheduling, a completed check, catching up, provider delay, and reconnect/consent requirements. Its status flag is an operator configuration—not evidence a scheduler has actually run. The private summaries page refreshes every 30 seconds only when there is no unsaved draft; this refresh reads saved results and does not perform ingestion.

## Task focus and helpful links

When Shared tasks refreshes, keyboard focus stays on the same control for the same task. If that control now does something different, focus returns to the task name. If the task leaves the current list, focus returns to the selected task view rather than another task.

Tasks can record an optional **Done when** outcome at creation, separately from the latest progress note. It stays visible through progress, completion reporting and verification. Enabled teammate task creation may include an outcome for new self-owned or unassigned work; changing an existing outcome remains organizer-only. Outcomes are shared planning text, not evidence that work is complete—keep private booking codes and credentials in Private details.

Manual **Create a linked task** also accepts its own optional **Done when** result. The child and relationship save together; the parent’s instructions and outcome are never copied or changed. Leaving the result blank stays supported. A recorded outcome does not accept or complete the task, and Related still does not gate the parent’s completion.

Organizers can use **Break down task** on an open task to review up to eight pasted titles. Nothing is selected by default. **Back to checklist** keeps the original text in the open dialog; when you review again, unchanged steps keep their edits and selections, while new or ambiguous steps start unchecked. Add or edit a separate Done when result, then save the selected steps and their Related links together. A confirmed save lists the new tasks with their owners and due dates. Open a step and choose **Edit owner and due date** to use the regular task editor. Saving returns to the batch if there are no other unsaved edits in the task. **Back to added tasks** also returns to the batch; closing the dialog ends this session. The steps start unassigned and To do; they do not block, reschedule, or complete the original task. Duplicate open titles and stale reviews are rejected. If Weft can’t confirm the save, it keeps the review and offers a read-only check of current links rather than resending or treating matching titles as proof. This manual flow does not call AI or send messages.

In a real project, **Draft smaller steps with AI** is a separate organizer action in the same dialog. The organizer sees the exact title before choosing to send it to Groq. The provider receives no event context, notes or member data, and cannot change the project. It returns up to five editable private suggestions; none are selected by default. The draft is stored separately from project-wide plans, counts against the existing AI planning allowance, and cannot be used after the source task changes. Ask Weft chat remains disabled.

In task details, **Clarify outcome** saves a reviewed change without changing status, progress-note attribution, owners, dates, schedules or links. A different outcome clears acceptance and Next up so the owner can reconfirm. The task conversation retains the old and new outcomes; no email is sent. **Reduce the scope** uses the same reconfirmation rule. Completed tasks and pending completion reports must be reviewed or reopened before changing the required outcome. Task-to-Weft breakdown requests still copy only the task title, not the outcome or task notes.

Organizers can use **Tasks → Assign tasks** to delegate selected open tasks from the current filtered view to one active teammate in a single reviewed save (up to 100 tasks). Nothing is selected by default; choose the owner and confirm the changes. Completed work and pending completion reports are excluded. Tasks already owned by that person stay unchanged. Reassignment resets the previous acceptance, Next up commitment and pending recovery requests, but preserves task progress, instructions, preparation deadlines, schedules and prerequisites. The new owner must accept responsibility separately. No messages are sent. Stale task reviews, removed teammates and changed organizer access cannot partially apply a batch.

Changing the recipient or selected tasks requires a new confirmation. If the project changes mid-review, **Refresh assignment review** checks the same filtered view or **Before the event** section without saving. Unchanged choices carry forward; changed or ineligible tasks are unchecked and an unavailable recipient is cleared. The organizer confirms the refreshed batch before saving.

In **Edit task details** and **Email briefing**, changing or removing the owner while a completion report is awaiting verification requires confirmation. The old report leaves the review queue, any saved evidence stays in task history, and the task stays incomplete. Leaving the owner unchanged does not trigger this confirmation.

Owners can commit to up to three actionable Next up tasks, propose a date or ask for help without changing the agreed plan. Pending requests remain visible in the owner's personal Next up panel even when they aren't commitments. The organizer and requester can read the latest explicit response in task details; the full decision and check-in stay in Comments. If the requester still owns the task, **My tasks → Review organizer response** opens that reply even when the work remains blocked or newer comments appear. Organizer decisions stay in Needs attention, and fixed external dates require explicit confirmation. Ranking considers essential work and downstream deadlines, not only overdue age. Waiting parents route attention to their prerequisites. These are in-app prompts, not background email reminders.

**Overview → Waiting for your review** brings pending teammate requests, completion reports and amended completion evidence together for the organizer. The oldest items appear first; expand to see the entire queue. **Timeline** flags scheduled activities with an active help request or date proposal, and **Before the event** links to those requests across all dates in its selected scope. If a newer plan is already known, **Refresh event review** reloads the facts without leaving the review or changing its scope. A decision form never auto-retries a stale save or discards unsaved text. The labels do not move activities or deadlines, and neither request notes nor pending-request labels are added to run sheet or guest agenda copies. If required work reopens, the completion report stays in the queue and opens **Task relationships**. The organizer can still request changes to the report, but can’t verify completion until the required work is resolved. Acknowledging an amendment does not reopen or reverify the task, and opening the queue never changes records.

When Next up is empty, actionable suggestions are shown directly; unavailable work and no assignments have distinct empty states. Personal suggestions prioritize the work itself (including urgent deadlines and prerequisites), not organizer reminders to follow up. At equal priority, accepted work comes first and is labeled separately from assignments still to review. Accepting an assignment does not commit it to Next up. Reassignment advice considers active teammates only.

Populated project Overviews start with **Your next steps** for the signed-in planner: their recorded Next up commitments and up to three actionable suggestions across remaining slots, not other people's assignments. **View my tasks** opens the existing personal task view and clears stale search/owner/status filters. Review a task before explicitly accepting responsibility, committing, reporting progress or completion. Displaying this panel makes no API/provider request or task changes; suggestions are not commitments, completion or a readiness score. Empty projects retain their role-aware starting guidance.

In **Your next steps** and **My tasks → Next up**, activity rows show the saved event-local time and location. A preparation deadline is labeled separately, and missing or invalid times are called out. **Show in Timeline** opens the saved start day and focuses the exact activity in the timetable, keeping the current All activities or My activities scope. **Schedule changes to review** stays visible even if work is blocked or all three commitment slots are full. If a task already has a help request or a returned report, its row includes the schedule review link without duplicating the task. In the activity’s schedule comparison, **Show current day in Timeline** opens the new day in context, including from an in-app notification. If the schedule was removed, the comparison says so and offers no day to open. These shortcuts don’t accept the assignment or change the schedule.

Completion labels distinguish the person who reported the work from the organizer who verified it. The same attribution appears in task details, linked results and summaries; historical records are not rewritten.

Saved task notes separately retain who recorded them and when. Verification, comments, attachment edits and task-detail changes do not take authorship of an unchanged note. The task list attributes its displayed note or latest comment to that record, while task details retain the saved note's attribution. Older notes without recording metadata explicitly say the author was not recorded; assignment or the last task editor is not used to guess an author. Reviewed email summaries are attributed to the person who recorded the note, not presented as text authored directly by the email sender.

Owners can open a ready task and choose **Report complete** to reveal a completion note followed by an optional **Add a file or link** section. Choosing a file makes no upload; **Submit completion** uploads it through the existing authenticated project-file route and then saves the report. Files use the existing 4 MB/type/access limits and remain shared with the project team in Event info. An upload failure does not submit completion; a saved file remains available if the later report save fails. Required prerequisites still gate reporting, and other people cannot report an owner's work. Attachments are shared context, not independent verification.

For completion awaiting required verification, organizers can choose **Request changes** and record a shared reason instead of verifying. The task stays incomplete, its agreed outcome and progress attribution stay unchanged, and its earlier report/evidence is retained in the task conversation and bounded evidence history (latest 10 entries). The owner sees **Changes requested**, can share progress, and can submit a new completion report. Resubmission supersedes the active request but does not verify the work; the organizer still explicitly verifies it. Changing the agreed outcome also supersedes the active changes request while preserving its conversation history. Only one competing verification/return decision can save from a reviewed revision. No email, AI call or external action is performed by returning a report.

The assigned owner can open returned work from **Your next steps** or **My tasks → Next up**. **Prepare revised report** beside the organizer's feedback opens the existing form without submitting or copying prior attachments. If required work is still open, the task stays visible for review, but the revised report cannot be prepared until the prerequisite is resolved.

With **In-app task reminders** enabled, **Notifications** shows returned reports first, then schedule changes to review, then due-date reminders. Returned reports and schedule changes appear even without a deadline. A task appears once. The schedule reminder shows the task name and opens the schedule comparison without accepting the assignment. Reminders are scoped to the current account, project, and browser. Nothing is sent by email or push.

Active completion changes requests remain visible in **Needs attention**, task-list responsibility labels, the live event schedule, **Before the event**, and scoped run-sheet snapshots. Future check-in dates or unfinished prerequisites do not hide the request from attention; those prerequisites still gate completion. Progress updates retain the request, while a fresh completion report replaces it with verification pending. Run sheets include only the changes-request label and count, never the review reason or earlier report. These are saved planning facts, not a readiness certification or an external notification.

New Helpful links searches are disabled by default during migration; unexpired cached links remain readable. Leave `GROQ_WEB_SEARCH_ENABLED` unset until a public-data smoke test confirms free-account `browser_search` access and provider-origin citation URLs compatible with the fail-closed parser; only then set it to `verified`. Do not use model-written URLs as citations or enable paid fallback. The adapter sends only task name, category and optional city/region, never notes, emails, comments, booking codes or participant profiles. Public HTTPS links are display-only; Weft never fetches those destinations or makes bookings. Existing 7-day caching, one lookup/task/minute and 25 lookups/account/day limits remain. Groq search access, source metadata and any separate search charges are unverified.

## Event information

### Event wrap-up

**Wrap up** (the existing `#memory` link still works) brings task close-out and team lessons together. All tasks or My tasks separates still-open work, completion awaiting required organizer verification, and recorded completions. Every task is counted once; all recorded completions are available, not just a recent preview. **Completion needs attention** links to returned reports and amended evidence within that scope, without copying report contents or changing the original verification. Open a task to use its normal progress, evidence and verification workflow. The event date never completes a task or closes the event. These are task counts, not an event-success or safety score.

Team lessons remain shared regardless of the task filter. Save an action to repeat or improve, its applicability and optional event rating; no rating is preselected. Saving a lesson neither creates a task nor sends a message. **Draft follow-up task** on an active lesson opens the existing permission-checked task form. Saving links the new task to that lesson in this project without copying any lesson text. If another tab changes the project, **Check latest lesson** keeps the entered fields intact. Review any revised lesson and select **Use this lesson** before saving separately. If the lesson is retired or task creation is no longer allowed, the form keeps the draft for reference but does not add it. **Open added task** takes you to the exact saved task; **Tasks linked to this lesson** shows its current status to the team even after reloading, dismissing the receipt, or retiring the lesson. These links stay visible in My tasks without changing that filter. Budget, guest/file records and private bookings remain separate and must be reviewed where relevant. No project archive, automatic completion, payment, external contact or new AI call is performed by this page.

### Event-day run sheet

Organizers can use **Timeline → Move event plan** to review a different event date and select individual preparation deadlines or activities to shift by the same number of calendar days. Nothing is selected automatically. Activity clock times and the event time zone stay fixed; ambiguous or nonexistent moved local times require separate editing. Fixed external deadlines and completed/reported work cannot be moved by this batch review. Changed tasks retain their owners and progress, but acceptance and Next up commitments are cleared for reconfirmation. Task history records the change. The event date and selected task dates save together, with stale-write and organizer-access checks.

Unselected tasks, catering cutoffs, budget due dates, bookings, saved planning briefs and availability-poll options stay unchanged. Review these separately, and check owner overlaps and dependencies in Before the event afterward. No invitations, messages, reservations or payments are made. Changing Project settings by itself still does not move task dates.

**Timeline → Before the event** reviews the current saved plan: open preparation, required verification, blocked work, ownership/acceptance, overdue deadlines, unfinished prerequisites, owner overlaps and missing activity details. It follows All/My scope (preparation-deadline view reviews all tasks). Sections can overlap; zero findings never certifies safety, approvals, bookings or readiness. After opening a task, **Back to event review** returns to the same section and recalculates it from the workspace’s current saved state. No automatic task changes or messages are made.

Organizers can fix missing activity times or locations from that review. **Back to event review** and a confirmed save both return to the same section. If the project changes, **Check latest schedule** keeps the entered values in place and reads the current plan without saving. If the activity and event time zone are unchanged, review the draft and select **Save schedule** separately. If the activity changed or an earlier save could not be confirmed, the draft stays visible but locked; return to the event review to use the current schedule.

The event schedule keeps unfinished activities in **Check progress** after their entered end time, or once a start time is reached without an end set. Open an activity to check with its owner and record the real outcome. Time alone never changes task status; reported work awaiting verification stays in the dated timetable rather than asking for another progress report. The section follows the current All activities / My activities scope and refreshes with the schedule clock.

If a live refresh moves a keyboard-focused activity, Timeline keeps focus on the same activity and brings it into view if needed. If it leaves the current scope, focus moves to the activity scope control or the schedule heading, not to another task.

Scheduled activities awaiting required organizer verification also appear in **Completion awaiting verification** in the live focus area, within the selected date and All activities / My activities scope. This includes historical Done records that still lack required verification. They are not labeled Scheduled now, Next or Check progress; the report is not proof of verified completion. In the live focus area and **Before the event**, organizer review links open the completion details, or **Task relationships** when required work blocks verification. Amendments open their evidence without changing verification. Teammates and historical records without a report keep the normal task link. These links don’t expose report text in the schedule or make decisions.

Timeline, Before the event and the team run sheet show **Review linked results** when a blocked task’s required prerequisites are all complete, including any required verification. The task still says Blocked: open it to review the results and check for other blockers before choosing to resume. Related links alone never trigger this cue, and result text is not included in the run sheet.

When activities are scheduled, **Timeline → Run sheet** opens a read-only snapshot of the current All activities or My activities view. It groups event-local times by date and shows activity names, locations, owners, status and entered overlap warnings. The copy highlights unassigned work and saved clock times that need correction. Completion awaiting verification stays distinct from Done. It never changes tasks or infers completion from the clock.

Print the run sheet or **Download text (.txt)** for an offline team copy. If downloading is unavailable, use **Show text to copy**. Both formats use the same snapshot, including warnings and any selected day. An empty view keeps its selected date and activity scope, explains how to find activities, and doesn’t export a blank schedule. Repeated print headers identify the event, time zone, scope and snapshot so detached pages can be placed in context. **Check for updates** checks the saved plan without editing it. If the connection stalls or fails, the check stops, and Weft says that you’re still looking at the last loaded copy. You can retry or use that copy offline unless Weft detected a conflicting or newer revision. Closing and reopening doesn’t bypass that warning. **Refresh run sheet** verifies the saved plan in the same date and activity scope; a failed or intermediate refresh leaves the old copy blocked. A downloaded copy is not live and cannot be recalled; confirm changes with the team before relying on it. It does not include task notes, evidence, guest records or private bookings, and downloading does not send anything.

Choose a date in Timeline or jump to the first, previous or next activity day. The date applies to the schedule and run sheet in either team scope. On a selected date, every activity still in progress past midnight appears with its original times. **All dates** also shows carryovers on displayed days, including their first and last continuation days; select a date to see an otherwise unlisted day in the middle of a long activity. Untimed activities stay in a separate list until scheduled.

If you move an activity from a Timeline row to a different date, the current date and activity scope stay put. On closing the editor, the save notice shows where the activity went. **Show saved day** switches to its new day and focuses the activity without changing your activity scope. Removing a time shows that the task was kept in Shared tasks.

From that untimed list, **Set start time** opens the named activity only. A confirmed save returns to the same Timeline view, shows the saved time, and explains if the selected date or **My activities** hides that row. **Open activity** still works from the confirmation without changing either filter.

When a schedule edit clears an existing acceptance, the assigned teammate can compare the earlier and current time and location in **Accept your task assignments** and task details. Subsequent edits before reacceptance preserve the earlier comparison point; schedule removal is shown as **Not on the schedule**. Older changes without a saved comparison continue to show the current plan. Opening the comparison doesn’t accept the task, change progress, or notify anyone. A reviewed email that says someone accepts the task doesn’t reconfirm an outstanding schedule change.

If the project changes while you’re reviewing assignments, **Refresh assignment review** reloads the same review without accepting anything. It keeps checked assignments that are still eligible and unchanged, and clears choices that changed or left the review. If the event time zone changed, check scheduled and schedule-change assignments again. A failed refresh keeps your selections visible and blocks acceptance until you can verify the saved plan.

In an individual task, **Accept responsibility** and adding an unaccepted task to **Next up** use the task and project revisions you reviewed. If the plan changed, **Refresh task review** loads the current details without accepting anything. It keeps unsaved text in place by waiting until you copy or clear it. After refreshing, review the current plan and choose whether to accept.

**Before the event** lists **Schedule changes awaiting owner acceptance** separately from assignments that haven’t been accepted. It shows the current activity time or that the activity is no longer on the schedule, including removed slots that no longer appear in Timeline. Scheduled rows also distinguish renewed acceptance from first-time acceptance. These cues don’t accept work on someone’s behalf or include the earlier schedule.

New or changed activity times must occur exactly once in the event time zone. A time skipped or repeated when clocks change needs a different local time. Project settings won't switch to a zone that makes a saved slot ambiguous or nonexistent. Older affected slots remain visible and editable, with warnings in Timeline, Before the event and the team run sheet. They don't get live clock cues and are excluded from new guest agendas until corrected. AI drafts keep the activity but leave invalid proposed times blank for review; approval rejects invalid times before adding any tasks.

Use **Copy day link** to share the live project date with a teammate. It does not grant access or send a message, and it does not copy your personal activity filter.

In the private plan, **Paste a checklist** imports one title per line without calling AI. Imported tasks start unchecked and unassigned. If the shared plan changes, recheck a pasted draft without losing edits before adding anything. Before adding any draft, **Selected items preview** distinguishes preparation tasks from activities with or without an entered start time. Untimed activities go into Shared tasks but need a start time before appearing on the timetable or run sheet. Locations entered without a time go into the shared task notes instead of the timetable.

After adding a reviewed plan, open a task directly from the receipt. The organizer can refresh **Team handoff** to see which new tasks need assignment or completion review, which are waiting for acceptance or a revised submission, and which have been accepted or completed. Completion links open the current evidence or **Task relationships** when required work blocks verification; if the review is no longer pending, the link opens the task normally. Returned work with no active owner appears under assignment so it doesn't stall unnoticed.

When a receipt opens the owner or start-time editor, **Back to plan receipt** reopens the current receipt and focuses that task’s row. Save any edits before going back; the return itself only reads the current receipt and does not assign, schedule or generate anything. If that task is no longer available, the planner explains why it cannot focus the row.

Verifying, returning a report for changes, and acknowledging amended evidence apply to the version the organizer reviewed. If the report changes, use **Refresh completion review** to see the current evidence without making a decision. An unsent note stays in place until you copy or clear it; review the refreshed evidence before submitting a decision. Acknowledging an amendment does not reverify the task.

Accepting a completion report from **Email briefing** records the reviewed note and links to that exact shared email from **Completion details**. Any previous submission, including its links and shared files, moves to **Earlier submissions**. No email attachments are imported, and a later email does not replace an already verified submission.

Completion details shows the recorder for each submission when known. **Earlier completion emails** keeps exact links to recently superseded email reports recorded by Weft, separately from earlier files and links. Older evidence without a saved source is not matched by its text or timestamp.

Use **Wrap up → Reuse tasks for another event** to choose and edit titles for that importer. Only reviewed titles carry forward; the source event and its task history are unchanged.

Organizers can use **Draft guest agenda** to turn selected activities into plain text for guests. The draft shows its date and whether it includes **My activities only** or **All activities**. From a personal draft, **Start over with all activities** keeps the date and leaves the Timeline filter unchanged; it confirms before discarding edits and starts with nothing selected. Review the guest-facing titles and add any locations you want to share. Owners, internal notes, and saved locations are not included. The draft is not saved or sent. Use **Copy guest agenda** to check the current schedule first. If automatic copy is unavailable, the checked text can be copied manually once. If a check can’t finish, retry without losing your edits; if a newer plan is found, start a fresh agenda from the updated schedule.

Run sheets label an inactive assigned person as **Inactive teammate** and a missing assigned member as **Assigned owner unavailable**, rather than calling either unassigned. A scoped warning calls out unresolved activities with either responsibility gap; completed, verified work keeps its historical owner label without an open-work warning. Confirm responsibility with the organizer. The snapshot does not reassign work or expose member identifiers or contact details.

Open activities assigned to active teammates show **Acceptance not recorded** when neither owner acceptance nor a completion report is recorded. When a schedule change cleared an existing acceptance, the Run sheet instead shows **Schedule changed · owner needs to accept again**. Separate counts cover only the scheduled activities in the selected scope, counting an overnight activity once even when it appears on more than one day. The copy includes the current schedule, not earlier times or locations. Removed activities remain in **Before the event**, not in the Run sheet timetable. Assignment alone does not confirm responsibility; check with the owner against the live plan.

Unresolved activities with unfinished required links show **Required work not complete**, separately from their recorded status. Required tasks elsewhere in the project still count in My activities; incomplete, unverified and missing prerequisites remain unresolved, while Related links do not block work. Only the warning is included, not prerequisite names or notes. Completing required work removes the warning in a newly opened snapshot but never automatically completes the activity or certifies event readiness.

Timeline and Run sheets mark **Location not set** and **No end time set** on the affected activities, without substituting the event venue or guessing a duration. The Run sheet also counts unresolved activities missing either detail in the selected date and owner scope. Overnight activities are counted once, even if they appear on more than one day. Confirm the missing details in the live Timeline before relying on a saved or printed copy.

In Weft, **Go to first activity with missing details** checks for a newer plan, then takes you to the affected Timeline row without changing the selected date or owner filter. If the sheet is out of date, refresh it first. The button isn’t included in printed or downloaded copies.

**Print / save PDF** opens the browser's print dialog; Weft does not send the sheet anywhere. Only the sheet is included in print styles, not the surrounding workspace. Notes, comments, email, guest records, files and private booking details are excluded. The snapshot is dated and not live: confirm later changes with the team, and share paper or saved copies only with people who need them. Downloaded copies cannot be recalled after access changes. Browser pagination and printer/PDF settings depend on the browser and device.

### Optional manual budget

The **Budget** page is off by default. Organizers can enable a single-currency tracker, set an optional target, and record costs with an estimate, commitment, net payment recorded, owner, due date and optional task link. Teammates can view; only organizers can edit. If a task or owner becomes unavailable, the existing cost can still be updated while keeping the old link for reference. Clearing or replacing it is optional; new links must point to a current task or teammate. This is a manual planning record: no payment, approval, reservation or task completion is executed. Do not enter bank/card information or private booking references.

Amounts use exact minor units. Blank amounts remain unknown, with partial totals labelled explicitly. Estimates, commitments and payments are separate totals, never summed together. Expected total uses the commitment when known, otherwise the estimate, and never less than the recorded payment. If an active cost has a payment but no estimate or commitment, the payment still counts toward the minimum shown; the final total and any remaining budget are unknown. If that minimum already exceeds the target, the page shows how far over it the budget is at a minimum. Cancelled costs retain net payments in totals; archiving hides a row but does not remove its costs. Currency is locked after the first cost; there is no conversion. Supported currencies are USD, CAD, EUR, GBP, AUD, JPY and KWD. Limits: 500 costs including archived records and the latest 100 changes in visible history. Turning the tracker off preserves its records.

Budget data uses the existing encrypted, project-scoped `project_info` sidecar, revision checks, retry receipts and write-time authorization. Task links are checked against the current project without modifying tasks. Budget amounts are not added to AI context or shared workspace exports. No schema migration is needed for this optional field.

If an existing cost changed while you were editing, **Review latest cost** checks the saved values without clearing your draft. Choose which values to keep for conflicting fields, or choose a complete set when status and amounts affect the forecast together. Applying choices updates only the draft. Choose **Save** separately to record it.

If a save can’t be confirmed, **Check if original saved** reads Recent budget changes without writing. In a real project, **Retry original change** resends only the original values with the same request ID. The demo allows a history check only because a reset can replace its Budget. A missing history entry does not prove that a save failed. Newer edits stay in the open editor and aren’t sent with the retry; review the latest cost before saving them. If you close an unconfirmed editor, check Recent budget changes before entering the same cost again.

Opening a linked task from Budget keeps the current active or archived cost view. Closing the task returns to the originating cost, even when another cost links to the same task. If the task link is no longer available, focus returns to the cost heading or the Budget section. Opening the link does not start a Helpful links search.

When the expected total is incomplete, Budget shows how many costs still need an amount in the current and archived lists. Use the review buttons to jump to the first flagged cost in either list. Each flagged cost explains which amount is missing; archived costs still count toward the same total.

### Private starting plans

An empty project’s Overview gives a role-aware starting point instead of an attention all-clear. Organizers can open the plan builder or add a task manually; opening the planner does not call AI. Teammates with task-creation permission can add a self-owned or unassigned task. Other teammates see that the organizer still needs to add work and can view People. Once tasks exist, the ordinary attention and completion panels return. No tasks, invitations or messages are created by displaying this guidance.

For multi-item drafts, **Select none** lets you start from just the items you need. **Select all new items** skips existing and repeated exact title/time matches without deciding possible semantic duplicates or replacing saved reuse choices. **Owner for selected items → Assign selected** changes only selected private proposals; existing draft owners on those proposals are replaced deliberately, while excluded/reused items, dates and prerequisites stay unchanged. Review and save/add normally; these controls do not call AI or update shared tasks by themselves.

Selected proposals show **Existing prerequisites** above their collapsed details. Open a matched task in a new tab to check the shared record without leaving the draft, or remove the proposed link without changing the shared task. A unique title/time match or a confirmed similar task can be reused; ambiguous exact matches are not picked automatically.

Organizers can open **Build a plan** from Overview or continue after creating a project. Choose an event type and **Use starter checklist** for a product-authored starting point without AI or AI quota. School and corporate checklists include more detailed preparation, delivery and follow-up; off-sites, trips, parties and anniversaries use proportional checklists. They are not tailored to the brief and do not establish safety, legal or organizational policy. Dates, times and owners start unset. Review, edit, exclude and assign items before explicitly adding them; existing work is not overwritten. Replacing a saved private draft requires confirmation, keeps shared tasks unchanged, and preserves AI cooldowns. Retries reuse one request ID; simultaneous or stale edits cannot silently replace a newer draft.

AI planning remains optional. A brief identifies the event type, intent, optional last day, and daily activity hours. Schools and corporate events have tailored planning guidance; off-sites, trips, parties and anniversaries share the same review flow. Saving a brief and opening the project do not call AI. **Generate draft** explicitly sends the brief, basic event details, up to 200 existing task titles/start times and eight relevant saved-feedback suggestions to Groq—not emails, contacts, uploads, booking records, member identities or progress comments. The organizer should avoid entering sensitive information in the brief itself.

Starting plans, gap suggestions and Ask Weft task proposals can include a separate **Proposed Done when** result. Every new product-authored starter item includes one. Review or edit it under Details before adding tasks; the reviewed result becomes the shared task’s persistent **Done when**, separate from instructions and later progress reports. It is a proposed requirement, not evidence, acceptance, approval or completion. Existing private drafts without this field remain blank rather than having their notes silently promoted to an agreed outcome. Editing a proposed outcome invalidates a prior semantic duplicate-reuse choice; reusing an existing task never changes that task’s outcome. AI is asked for short observable results, with unknown requirements left blank; live output quality still needs separate authorized verification.

Ask Weft’s private written drafts have explicit **Copy draft** and **Download draft (.txt)** controls. They contain only the displayed written title, complete text and review reminder, not the conversation, research results or project records. Downloads are plain UTF-8 text generated locally; neither action makes an API/provider call, shares with teammates, sends a message or marks work complete. If clipboard access is unavailable, use the download or select the text manually. Review facts and placeholders before using the result; copied/downloaded text remains on your device until you remove it.

Responses use Groq’s `openai/gpt-oss-20b`, low reasoning effort, no tools, strict structured output and independent validation. The model name does not send data to OpenAI. Output is capped at 4,000 tokens including reasoning. A conservative full-payload size guard runs before consuming the daily allowance; oversized contexts require a shorter brief or manual planning, without silent truncation. Proposed dates and activity windows are checked; unknown times stay unscheduled. Daily end must follow start; leave daily end blank and supply a last day for overnight activities. Questions and assumptions stay separate from tasks. This is a draft, not a verified safety checklist or reservation service. No messages, bookings or purchases are made. Attempts are capped at one per project/minute and five per account/UTC day across real projects and demo; provider failures count. Reads never trigger generation. Stale clients without Groq-specific consent cannot generate.

The encrypted, organizer-only `plan_drafts` sidecar (additive migration `0009`) is excluded from shared workspace snapshots/exports and isolated by demo generation. The organizer edits titles, notes, owners, dates, optional activity locations and prerequisites, then explicitly adds selected items. A selected item cannot depend on an unchecked item. The approval validates all items before a single workspace/receipt transaction; retries cannot duplicate tasks. Existing work is preserved. Approved tasks use the normal claims, progress, dependencies and event schedule, not a second task system. If saving private edits reveals a newer project revision, Weft keeps the saved edits and stops before adding tasks. Review again before confirming; a change to the draft’s planning context may also require rechecking or replacing the draft. If another tab replaces the private draft while it is being saved for approval, Weft leaves the current edits visible and does not apply the other tab’s version. A failed provider request retains the prior usable draft; rate-limit/credential failures are shown without fabricating an AI result.

If **Add selected items** in the plan builder or **Add task** on a suggestion card loses its response, **Check what was added** looks for the receipt for that exact draft and selection. Checking never adds tasks or calls AI. A conflict requires a fresh read before approval can be tried again; if another tab changed the saved draft, reload it explicitly to review that version. Nothing is reapplied automatically. After an unconfirmed suggestion approval, automatic generation stays paused in that sidebar until you explicitly refresh suggestions.

Server and hook-level UI tests cover authorization, privacy, stale writes, retries, concurrent approvals, access changes, expired leases, provider consent, demo resets and failed requests. Hook tests do not verify browser rendering. Live quality remains unverified until Groq setup, authorized publication and browser QA are complete. See [Groq Responses](https://console.groq.com/docs/responses-api), [structured outputs](https://console.groq.com/docs/structured-outputs), [free-plan limits](https://console.groq.com/docs/rate-limits) and [data controls](https://console.groq.com/docs/your-data).

### Schedule and shared information

Timeline has an event schedule and a preparation-deadline view. Organizers can add activities or schedule existing tasks with local start/end dates and a location. Every activity uses the same task, owner, comments, blockers and completion flow; completed activities remain visible. Adding, changing or removing a schedule on open, accepted work clears its acceptance and Next up commitment so the same owner can reconfirm. The assignment review shows the current time and location. Unchanged schedules and completed or reported work keep their recorded commitments and evidence. Removing a schedule entry does not delete its task; scheduling does not change preparation deadlines, progress or send a message.

Project settings stores the event time zone explicitly; all teammates see event-local times. Multi-day and overnight activities have their own dates. Changing the event date never moves activities automatically; changing a zone with scheduled work requires acknowledgment and preserves the entered clock times. This is a timetable, not background reminders or automatic status changes. Fresh/restarted demos include three sample activities; real projects stay empty.

The event schedule shows the current scheduled slot and the next start time, including simultaneous activities. Clock cues refresh every minute and on return to the page, in the event time zone, without changing task status or interrupting an open task dialog. Finished work and completion reports awaiting verification stay in the timetable but are excluded from these focus cues. Activities without an end time are never assumed to run indefinitely; once their start is reached they say that the end is not set. “Past scheduled end” means the entered time has passed, not that the app observed a delay. The full schedule remains available below the focus strip.

Teammates can switch between **All activities** and **My activities**. The timetable and current/next cues use the same owner filter; completed activities remain in the timetable. Focus cards show the location, owner and reported status, and open the normal task details. Filtering changes only the view, not ownership, shared data or permissions.

Deadline labels, Needs attention ranking, recovery check-in dates, AI starting-plan dates and time-driven planning suggestions use that same event time zone, rather than each teammate's browser zone. Projects without a time zone use UTC until the organizer sets one. Calendar-day changes do not rewrite stored due dates or progress timestamps; inactivity still measures elapsed time. Provider usage quotas remain account-wide UTC days.

The event schedule flags unfinished activities assigned to the same person at overlapping times. Task details link to the other activities; the organizer can adjust times or ownership using the existing controls. Warnings recalculate from saved tasks and never prevent saving, change progress, or reschedule work automatically. Touching endpoints do not overlap. Missing end times are not guessed: only identical starts or a start inside a known time window can be flagged. Completed, verified work and unassigned activities are excluded. This checks assigned owners, not guest availability, shared rooms, travel time or external calendars.

**Potential location overlap** separately flags unresolved activities with matching location labels at overlapping entered times, even when different people or no owner are assigned. Matching ignores case, extra whitespace and compatibility-character differences; it does not infer that different labels refer to the same space. Timeline’s live activity cards and dated rows show owner and potential location overlaps for the date represented by that card or row. Task details link to the competing activities, and the warnings also appear in Before the event and the run sheet. My activities compares locations against the full project schedule but shows only your rows. Required verification still pending remains unresolved; completed/verified work is excluded. Missing end times use the same conservative rule as owner overlaps.

A shared or divisible space may intentionally host simultaneous activities. These warnings do not establish a booking, exclusive room use or capacity; aliases, external bookings, travel time and other projects are not checked. Confirm with the team, then explicitly edit the activity time or location if needed. No task status, ownership, reservation, message or shared data changes just by viewing a warning.

Event info keeps a guest list and shared files separate from task conversations. Guests have a contact name, optional email/phone, type (attendee, speaker, volunteer or vendor), group, attendance and notes. These are contact records, not accounts or app members. No messages, invitations or RSVP requests are sent to these guest records. Expected guest counts and other planning context remain manually maintained.

Project members can record a confirmed guest arrival without changing the RSVP. Search by name, email, phone, or group. Search ignores Latin accents and phone formatting, and **Clear filters** keeps you in the active or archived list you were viewing. If someone changes the list before your save, **Review latest record** reloads that guest without repeating your action. If the latest record already matches, the review is read-only; otherwise, confirm again after reviewing. Clearing an arrival corrects the record; it does not record a departure.

Authenticated project members can add/edit guests and upload files. Organizers can archive/restore guests; uploaders and organizers can archive/restore files. The four demo perspectives use the same interface and APIs with isolated sample contacts; restarting the demo isolates its old records from the new generation. Guest contacts do not grant app membership.

CSV imports require a preview and confirmation. Invalid rows prevent the entire import; existing emails (including archived guests) are skipped rather than overwritten. Names alone never merge records. Limits: 40 KB / 100 rows per import, 500 guest records including archived contacts. Data uses revision checks and idempotent write receipts to avoid silent overwrite and duplicate retries.

Guest records and file contents are encrypted with context-bound AES-GCM. They are not included in task exports, task AI searches, or browser localStorage. Project uploads use a private Vercel Blob store with authenticated attachment-only downloads; upload is unavailable until that store is configured. Allowed formats: PDF, TXT, CSV, PNG, JPEG, DOCX and XLSX, up to 4 MB each. A per-authenticated-account cap of 50 MB / 200 uploads includes archived files and previous demo generations. Archive is recoverable, not permanent deletion or quota reclamation; retention/deletion administration remains future work. Files are not malware-scanned. Upload only information the project team is permitted to access.

Connected private Blob stores can use `BLOB_STORE_ID` with the SDK's automatically refreshed Vercel OIDC credentials; no long-lived read/write token is required. An explicitly configured `BLOB_READ_WRITE_TOKEN` remains supported and takes precedence. Never persist an OIDC token in code or copy production credentials into previews. The Files view offers upload only when the server reports storage configured; the guest list and CSV imports remain usable without it. Configuration is not proof of successful storage access: verify an authenticated fictional upload/download after connecting a store. Provisioning a usage-billed store requires owner approval.

## Build and validation

Use Node.js 22.13 or newer and the checked-in lockfile. `npm ci` installs dependencies. `npm run dev` prepares the legacy workspace assets and starts Next.js. `npm run build` prepares the same assets and builds the Next.js app; `npm start` serves that production build. Vercel must use the **Next.js** framework preset with no custom `dist` output directory.

`npm run typecheck` checks the app. `npm test` runs task reporting, dependencies, email briefing, concurrency, authorization, encryption, Gmail, demo and Vercel-adapter regression tests. Auth/provider tests use mocks; database tests use isolated SQLite/libSQL fixtures. Those tests do not prove Google OAuth, hosted storage or real email delivery works. Test mocks are not part of the production runtime.

The app imports the unchanged shadcn 4.18.0 stylesheet from `app/vendor/`, with its MIT license, instead of installing the full component-generator CLI during every build. UI components remain in the repository; this does not remove their runtime libraries. A checksum test protects that stylesheet from accidental changes. The formatter uses a patched Tinypool release. A scoped override pins `@esbuild-kit/core-utils` to esbuild 0.25.12 (the patched line already used by Drizzle); revisit it when Drizzle removes its deprecated loader. Dependency changes must pass a clean install, full tests/build, and an isolated migration-generation smoke test without touching production migrations or databases. A clean audit is a point-in-time advisory check, not a security guarantee.

The existing SQL migrations (`0000`–`0009`) remain unchanged in `drizzle/`; `0010` adds the first-task onboarding milestone table and `0011` adds daily product-activity counts. Schema source is `db/schema.ts`. Apply migrations only with the explicit, target-confirmed [migration procedure](docs/vercel-deployment.md#initialize-an-isolated-database). Builds and requests do not migrate databases. Runtime secrets belong in environment-scoped Vercel configuration or ignored local files, never in `.openai/hosting.json`, source or Git. [.env.example](.env.example) lists the required and optional variables.

Run fresh tests, type checks, build and dependency audit for the exact revision under review; historical test counts and dependency-audit results are not release evidence. Hosted sign-in, multi-user isolation, private file upload/download, invitations and Gmail ingestion still require the runbook's staged smoke checks. Groq is not configured or verified by this migration. The feature-detected WebMCP tools also remain unverified in a supported browser. This pilot has not had an independent security assessment.
