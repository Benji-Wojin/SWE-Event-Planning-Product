# Weft — private event planning pilot

Event planning with Google sign-in, a server-backed project workspace, and encrypted organizer-only booking details. This branch adapts the app to Next.js on Vercel, Turso/libSQL and private Vercel Blob storage. New real workspaces start empty; the Field Day sample remains in the separate demo.

The Vercel migration is not a completed hosted rollout: credentials, isolated storage, Google callbacks and live end-to-end checks still need configuration and verification. The existing private Sites app and its data remain untouched; nothing is copied or linked automatically. Follow the [Vercel deployment runbook](docs/vercel-deployment.md). Pushing and publishing require owner approval of the reviewed revision under [the engineering loop](docs/engineering-loop.md).

## Implemented behavior

- Tasks, owner acceptance, completion reports, organizer verification, comments, follow-up drafts, event context, and contextual feedback rules use durable Turso/libSQL storage through the existing SQL interface.
- Project APIs check authenticated membership server-side. Google sign-in requires a verified email and establishes a stable `google:<sub>` identity; incoming Sites identity headers are never trusted. The initial owner is bootstrapped from the configured allowlisted email. Teammates join individual projects using email-specific, expiring invitation links. Browser actor selection cannot grant permissions.
- Workspace writes use a compare-and-swap revision. Other-tab conflicts require an explicit page reload; drafts are never silently rebased onto newer data.
- Flight/hotel/transport/venue references are encrypted using AES-256-GCM with a separate secret server key. Gmail credentials and text previews use distinct authenticated encryption contexts. Private data never goes into shared exports, browser localStorage, or task notes automatically.
- Gmail imports use read-only Web OAuth, PKCE, expiring single-use state bound to the signed-in owner, server-side refresh tokens, and revocation. After authorizing Gmail, select projects and separately approve automatic AI checks. A separate dedicated Gmail connection sends project invitations with `gmail.send`, `openid` and `email` permissions; it does not read that mailbox.
- Automatic detection drafts private summaries of matching or possibly related incoming emails. The organizer can edit the summary, correct its project, and explicitly approve sharing; tasks still require a separate approval. Manual label import remains available under advanced settings. Private views show the 100 most recent matching imports, with originals collapsed and encrypted separately.

## Projects and setup

`/` is the Projects homepage. `/setup` creates a separate, empty project and then opens the optional `/plan?project=<id>` review step; `/setup?project=<id>` edits only that project's settings. `/project?project=<id>` opens its workspace. Creation is authenticated, server-persisted and retry-safe, independent of AI availability. Existing data stays under `main`; no tasks, guests, files or bookings are moved or cleared. New projects use an owner-authorized registry and explicit URL IDs so two tabs cannot switch each other's active project. Migration `0004` adds the registry and a booking scope defaulting to `main` for old records.

Gmail and guest-list imports are optional. The Gmail connection and optional manual label remain account-wide. Automatic matches are privately associated with one selected project; legacy manual imports remain available across the owner's projects. Reviewed summaries explicitly target a project. Tasks, guests, files, private bookings, suggestions and resource caches are project-scoped. Setup uses organizer authorization, origin verification, field validation and revision-checked edits. Failed saves preserve form values. Event date and location are optional. There is a 100-new-project organizer limit.

## Accounts and invitations

`/account` shows the current Google identity and sign-out. Organizers open **People → Team access** (or Invite), connect the dedicated Weft Gmail account, enter a teammate's Google sign-in email, and choose **Send invitation**. `/join?invite=…` checks the email before displaying project details; accepting atomically creates or reuses the account and grants access to that project. Links are single-use, expire in 7 days, and can be revoked. Creation and acceptance retries do not duplicate members. Tokens are stored as hashes plus an organizer-readable encrypted copy, never in shared task state.

Invitation setup uses the owner-configured Google Web client and `/api/gmail/callback` URI, distinct from sign-in's `/api/auth/callback/google`. Enable Gmail API, add the dedicated account as a testing user when applicable, and configure `gmail.send`, `openid` and `email` scopes. The owner configures the client and connects the dedicated account once; invitees need no Google API setup. Google UserInfo verifies the sender address. Import and sender connections must use different accounts; separate encrypted tokens, state tables and commit guards prevent one connection from replacing the other. Migration `0006` adds sender authorization, delivery state and send-attempt records without modifying existing invitations.

Only an explicit organizer action sends an invitation. Its recipient, project name and acceptance URL are server-owned. Durable send claims prevent double-click/network retries from dispatching twice. Status is **sent** only after Gmail returns a message ID; this means Gmail accepted the request, not guaranteed inbox delivery. Definitive rejection permits a manual retry after a minute; timeout, ambiguous errors, or an unrecorded receipt become **sending not confirmed**, never automatically retried. Check Gmail's Sent folder before revoking/replacing an uncertain invitation. Limits: 3 attempts per invitation and 50 attempts per rolling 24 hours across the organizer's projects. No guest-list mail or automatic task reminders are sent.

Google sign-in is authentication, not project access. Invited teammates see only their joined projects, can claim unassigned tasks, report their own progress/completion, comment, and contribute guest records/files. They cannot edit task metadata, manage access, connect Gmail, read private bookings/original emails, or use the owner's demo. There is no password database or separate password-reset flow. Sign-out requires confirmation and a CSRF-protected POST. If a Vercel deployment also has Deployment Protection enabled, a tester needs that separate platform admission; app invitations do not change it. The old private Site retains its existing access policy.

Removing access preserves task/comment history and marks the teammate inactive for new assignments. Server writes recheck active membership and its generation at commit, so remove/reinvite cannot revive stale task, file or helpful-link requests. Workspace revisions advance on team changes; open clients refresh every 20 seconds or on focus, and stop displaying a project when access is denied. Previously downloaded information cannot be recalled. Limits per project: 50 active teammates, 500 historical memberships and 500 invitations total. Migration `0005` adds project memberships and invitations without changing existing projects or ciphertext.

The homepage adapts `ProjectsHome.tsx` and `projects-home.css` from the existing Gather Lovable design workspace, commit `f7669b53ebacbefa76e8bf8f85e8cd28dae997d4`. It uses Gather's existing theme and validated setup form. Lovable preview data and storage are not part of the production app.

## Pilot boundaries

- Project data remains restricted by server-side membership. The Vercel sign-in page may be publicly reachable; it is not a replacement for Deployment Protection when an entire preview must be private. No access settings on the existing private Site are changed. Account-free attendee links are not enabled. Teammates retained in older sample workspaces are examples, not real accounts.
- Continuous planning checks and shared task-change suggestions use conservative local rules and event feedback. Organizer-requested starting plans and private Gmail relevance checks use Groq Responses structured output and the server-only `GROQ_API_KEY`. There is no OpenAI or paid-provider fallback. No autonomous email sending, live RSVP integration, or Gmail push notifications. Closed-app email checks require the verified cloud schedule below.

Planning suggestions recalculate on workspace reads and edits. Visible workspaces check for changes every 20 seconds (4 seconds in the demo), when Suggestions opens, and when returning to the page, including browser Back. Clock-driven checks can update without a saved project edit. The open Suggestions panel refreshes in place; task, guest and email drafts defer shared-state updates until safe. Covered and dismissed checks stay suppressed. Nothing runs while the app is closed; reopening checks the current state and time. Suggestions do not automatically create tasks.
- Google OAuth needs an actual Google Cloud Web client: enable Gmail API, configure consent/testing users and the relevant import/sending scopes, and add the exact redirect URI displayed in settings. Google may require verification for wider deployment; testing grants may need reconnecting after seven days.
- Gmail ingestion tests use mocked provider responses; they do not prove live mailbox ingestion. Do not enter passport or payment-card data. This pilot has not had an independent security assessment.
- Import disconnect revokes Google's import-account grant but retains imported previews and shared summaries. Sender disconnect removes its tokens and pending authorizations from Weft; Google grant revocation is available in the dedicated account's Google settings. Already-dispatched email cannot be recalled. Changing the Google client while either connection is active is denied. Original retention controls and account deletion UI are future work.
- Editing `GATHER_OWNER_EMAIL` does not revoke an already-bound owner: ownership changes need deliberate membership migration. Do not rotate the encryption key without migrating existing ciphertext.
- Private view hiding clears visible records but is not sign-out. Use Sign out to terminate account access.

## Automatic Gmail checks

Publication, a Groq free account/key, fresh mailbox consent and an authenticated cloud schedule must all be verified before calling detection live. Tests use mocked responses, not live email. Stay on Groq’s Free plan without enabling billing: free access is an account setting, not an API flag. Enable Zero Data Retention in Groq Data Controls before processing private emails. Ordinary users need no Groq account or key.

The owner selects up to ten owned projects and explicitly consents to sending email text plus project names/date/location and up to 60 active task titles per project to Groq. No guests, uploaded files, booking records, task comments or attachments are included. Text previews are limited to 24,000 characters, with the first 12,000 eligible for classification. Requests use no tools, strict structured output and server validation. Groq does not support the OpenAI `store` request option; retention is controlled by the Groq account. Clearly unrelated content is discarded; only opaque, expiring deduplication receipts remain. Matching/uncertain originals and drafts are encrypted; nothing is automatically shared. AI relevance and summaries can be wrong. Old provider consent never authorizes Groq: jobs pause before network access until fresh versioned consent. Re-consent preserves checkpoints, pending IDs, receipts and private summaries.

Initial enrollment scans the last seven days. Gmail history then catches incoming messages without labels, including archived mail and self-addressed mail. The initial history anchor is saved before backfill; page queues are checkpointed before processing and the final history ID advances only after processing every candidate. A 404-expired history cursor starts a disclosed seven-day recovery; earlier gaps can require manual import. Reconnecting or changing the Gmail label invalidates enrollment, requiring re-enabling detection. Pause keeps existing imports; re-enabling the same connection and project set resumes saved progress.

Each bounded run handles at most one queued message, one Gmail page and one AI request to reduce free-tier token bursts. Catch-up is gradual, not instant. Database leases prevent overlapping workers and stale writes; the pinned Gmail token cannot switch mailboxes mid-run. Attempts are capped at 250 candidate emails per account/day, including provider failures. A full-payload size guard rejects oversized context before consuming this allowance; it pauses checks with guidance instead of repeatedly retrying an oversized request. Queued emails remain intact. This guard is not an exact tokenizer or a guarantee of remaining provider quota. Groq 429 responses retain the cursor and respect bounded Retry-After backoff (one hour when absent); credential failures are paced hourly. Existing imports are not duplicated. Migration `0008` remains unchanged.

### Cloud runner setup and operation

Background checks are **off by default** and no cron schedule is included in `vercel.json`. After Groq setup, mailbox authorization, fresh AI consent and an explicitly approved schedule, the operator may enable `GMAIL_BACKGROUND_MODE=vercel-cron` with a random server-only `CRON_SECRET` of at least 32 characters. Vercel Cron then makes an authenticated `GET /api/gmail/automatic-run`, passing the secret as a bearer token. The endpoint rejects unauthenticated calls, caller identity headers, Origin headers and query overrides. It only processes already-enrolled, still-authorized mailboxes; it cannot create consent or impersonate a user.

Do not reuse the old Sites dispatch credential or `owner-private` mode on Vercel. Follow the [runner activation and verification steps](docs/vercel-deployment.md#optional-background-gmail-checks). A successful HTTP response or `not_due` result alone is not proof that an email was ingested. Groq credentials, live mailbox ingestion and unattended scheduling remain unverified until that full flow is exercised.

The settings page distinguishes configured background scheduling, a completed check, catching up, provider delay, and reconnect/consent requirements. Its status flag is an operator configuration—not evidence a scheduler has actually run. The private summaries page refreshes every 30 seconds only when there is no unsaved draft; this refresh reads saved results and does not perform ingestion.

## Task focus and helpful links

Owners can commit to up to three actionable Next up tasks, propose a date or ask for help without changing the agreed plan. Organizer decisions stay in Needs attention. Decisions record a check-in, deadline history and an owner-visible comment; fixed external dates require explicit confirmation. Ranking considers essential work and downstream deadlines, not only overdue age. Waiting parents route attention to their prerequisites. These are in-app prompts, not background email reminders.

New Helpful links searches are disabled by default during migration; unexpired cached links remain readable. Leave `GROQ_WEB_SEARCH_ENABLED` unset until a public-data smoke test confirms free-account `browser_search` access and provider-origin citation URLs compatible with the fail-closed parser; only then set it to `verified`. Do not use model-written URLs as citations or enable paid fallback. The adapter sends only task name, category and optional city/region, never notes, emails, comments, booking codes or participant profiles. Public HTTPS links are display-only; Weft never fetches those destinations or makes bookings. Existing 7-day caching, one lookup/task/minute and 25 lookups/account/day limits remain. Groq search access, source metadata and any separate search charges are unverified.

## Event information

### Private starting plans

Organizers can open **Draft a plan with AI** from Overview or continue after creating a project. A brief identifies the event type, intent, optional last day, and daily activity hours. Schools and corporate events have tailored planning guidance; off-sites, trips, parties and anniversaries share the same review flow. Saving a brief and opening the project do not call AI. **Generate draft** explicitly sends the brief, basic event details, up to 200 existing task titles/start times and eight relevant saved-feedback suggestions to Groq—not emails, contacts, uploads, booking records, member identities or progress comments. The organizer should avoid entering sensitive information in the brief itself.

Responses use Groq’s `openai/gpt-oss-20b`, low reasoning effort, no tools, strict structured output and independent validation. The model name does not send data to OpenAI. Output is capped at 4,000 tokens including reasoning. A conservative full-payload size guard runs before consuming the daily allowance; oversized contexts require a shorter brief or manual planning, without silent truncation. Proposed dates and activity windows are checked; unknown times stay unscheduled. Daily end must follow start; leave daily end blank and supply a last day for overnight activities. Questions and assumptions stay separate from tasks. This is a draft, not a verified safety checklist or reservation service. No messages, bookings or purchases are made. Attempts are capped at one per project/minute and five per account/UTC day across real projects and demo; provider failures count. Reads never trigger generation. Stale clients without Groq-specific consent cannot generate.

The encrypted, organizer-only `plan_drafts` sidecar (additive migration `0009`) is excluded from shared workspace snapshots/exports and isolated by demo generation. The organizer edits titles, notes, owners, dates, optional activity locations and prerequisites, then explicitly adds selected items. A selected item cannot depend on an unchecked item. The approval validates all items before a single workspace/receipt transaction; retries cannot duplicate tasks. Existing work is preserved. Approved tasks use the normal claims, progress, dependencies and event schedule, not a second task system. Changed project context requires review or regeneration. A failed provider request retains the prior usable draft; rate-limit/credential failures are shown without fabricating an AI result.

Server and hook-level UI tests cover authorization, privacy, stale writes, retries, concurrent approvals, access changes, expired leases, provider consent, demo resets and failed requests. Hook tests do not verify browser rendering. Live quality remains unverified until Groq setup, authorized publication and browser QA are complete. See [Groq Responses](https://console.groq.com/docs/responses-api), [structured outputs](https://console.groq.com/docs/structured-outputs), [free-plan limits](https://console.groq.com/docs/rate-limits) and [data controls](https://console.groq.com/docs/your-data).

### Schedule and shared information

Timeline has an event schedule and a preparation-deadline view. Organizers can add activities or schedule existing tasks with local start/end dates and a location. Every activity uses the same task, owner, comments, blockers and completion flow; completed activities remain visible. Removing a schedule entry does not delete its task. Preparation deadlines and progress timestamps are not changed by scheduling.

Project settings stores the event time zone explicitly; all teammates see event-local times. Multi-day and overnight activities have their own dates. Changing the event date never moves activities automatically; changing a zone with scheduled work requires acknowledgment and preserves the entered clock times. This is a timetable, not background reminders or automatic status changes. Fresh/restarted demos include three sample activities; real projects stay empty.

Deadline labels, Needs attention ranking, recovery check-in dates, AI starting-plan dates and time-driven planning suggestions use that same event time zone, rather than each teammate's browser zone. Projects without a time zone use UTC until the organizer sets one. Calendar-day changes do not rewrite stored due dates or progress timestamps; inactivity still measures elapsed time. Provider usage quotas remain account-wide UTC days.

Event info keeps a guest list and shared files separate from task conversations. Guests have a contact name, optional email/phone, type (attendee, speaker, volunteer or vendor), group, attendance and notes. These are contact records, not accounts or app members. No messages, invitations or RSVP requests are sent to these guest records. Expected guest counts and other planning context remain manually maintained.

Authenticated project members can add/edit guests and upload files. Organizers can archive/restore guests; uploaders and organizers can archive/restore files. The four demo perspectives use the same interface and APIs with isolated sample contacts; restarting the demo isolates its old records from the new generation. Guest contacts do not grant app membership.

CSV imports require a preview and confirmation. Invalid rows prevent the entire import; existing emails (including archived guests) are skipped rather than overwritten. Names alone never merge records. Limits: 40 KB / 100 rows per import, 500 guest records including archived contacts. Data uses revision checks and idempotent write receipts to avoid silent overwrite and duplicate retries.

Guest records and file contents are encrypted with context-bound AES-GCM. They are not included in task exports, task AI searches, or browser localStorage. Project uploads use a private Vercel Blob store with authenticated attachment-only downloads; upload is unavailable until that store is configured. Allowed formats: PDF, TXT, CSV, PNG, JPEG, DOCX and XLSX, up to 4 MB each. A per-authenticated-account cap of 50 MB / 200 uploads includes archived files and previous demo generations. Archive is recoverable, not permanent deletion or quota reclamation; retention/deletion administration remains future work. Files are not malware-scanned. Upload only information the project team is permitted to access.

## Build and validation

Use Node.js 22.13 or newer and the checked-in lockfile. `npm ci` installs dependencies. `npm run dev` prepares the legacy workspace assets and starts Next.js. `npm run build` prepares the same assets and builds the Next.js app; `npm start` serves that production build. Vercel must use the **Next.js** framework preset with no custom `dist` output directory.

`npm run typecheck` checks the app. `npm test` runs task reporting, dependencies, email briefing, concurrency, authorization, encryption, Gmail, demo and Vercel-adapter regression tests. Auth/provider tests use mocks; database tests use isolated SQLite/libSQL fixtures. Those tests do not prove Google OAuth, hosted storage or real email delivery works. Test mocks are not part of the production runtime.

The ten existing SQL migrations (`0000`–`0009`) remain unchanged in `drizzle/`; schema source is `db/schema.ts`. Apply them only with the explicit, target-confirmed [migration procedure](docs/vercel-deployment.md#initialize-an-isolated-database). Builds and requests do not migrate databases. Runtime secrets belong in environment-scoped Vercel configuration or ignored local files, never in `.openai/hosting.json`, source or Git. [.env.example](.env.example) lists the required and optional variables.

Run fresh tests, type checks, build and dependency audit for the exact revision under review; historical test counts and dependency-audit results are not release evidence. Hosted sign-in, multi-user isolation, private file upload/download, invitations and Gmail ingestion still require the runbook's staged smoke checks. Groq is not configured or verified by this migration. The feature-detected WebMCP tools also remain unverified in a supported browser. This pilot has not had an independent security assessment.
